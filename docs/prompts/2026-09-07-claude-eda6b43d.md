````text
Yes, in three layers, and they fit together well for this project.

**Wrangler environments** are the main tool for the API. An `env` block in `wrangler.jsonc` defines a named variant, and `--env staging` on `dev`, `deploy`, or `secret put` selects it. Each environment deploys as a separate Worker named `media-digest-api-staging`, with its own Durable Object storage, its own secrets, and its own URL. Two rules matter:

- **Bindings and vars are not inherited.** Each environment restates `vars`, `durable_objects`, and later `ai` and `vectorize`. Top-level settings such as `main`, `compatibility_date`, and the migrations list are inherited.
- **Local dev follows the same switch.** `wrangler dev --env staging` reads `.dev.vars.staging` instead of `.dev.vars`, and only that file.

A staging block here would look like this, with the top level staying production:

```jsonc
"env": {
  "staging": {
    "vars": { "WEB_ORIGINS": "https://*.media-digest.pages.dev" },
    "durable_objects": {
      "bindings": [
        { "name": "REGISTRY_DO", "class_name": "RegistryDO" },
        { "name": "USER_DO", "class_name": "UserDO" }
      ]
    }
  }
}
```

Because staging is a separate Worker, it gets its own Registry, its own owner seed, and in M3 its own Vectorize index such as `media-rag-staging`. That isolation is the point, and also the cost: two catalogs to ingest, twice the Workers AI usage.
````

```text
what is an embedding model - how is it different from the model used to query transcripts. why does embedding require a model at all
```

### Replied · 2026-09-08 21:57

```text
An embedding model turns a piece of text into a list of numbers, a vector, such that texts with similar meaning end up with nearby vectors. In this project it is `bge-base-en-v1.5`, and every vector has 768 numbers. That is all it does. It never writes a word.

**How it differs from the chat model.** The chat model, Llama 3.3 70B here, reads a prompt and generates text: a summary, an answer, a list of takeaways. It is large, slow, and expensive per call because generating language is hard. The embedding model is small and fast because its job is narrower: read text, emit coordinates. The two are used at different moments:

| | Embedding model | Chat model |
|---|---|---|
| Input | A transcript chunk, or a user's question | A prompt with instructions and context |
| Output | 768 numbers | Prose |
| When it runs | Once per chunk at ingestion, once per question at chat time | Once per summary at ingestion, once per answer at chat time |
| Purpose | Find the relevant chunks | Write something from them |

In M4 a question flows through both. The question is embedded, Vectorize finds the chunks whose vectors are closest to it, and those chunks are handed to the chat model as context so it can answer with citations. The embedding model decides what the chat model gets to read.

**Why embedding needs a model at all.** The alternative is keyword search, and keyword search cannot see meaning. A transcript that says "the Fed raised rates" will never match the question "what happened with interest rates" on words alone, and "bank" in a finance video has nothing to do with "bank" in a kayaking video. Nothing about the characters in a sentence tells you what it means, so something has to have learned what words mean from a very large amount of text. That learned knowledge is the model. It has read enough to place "raised rates" and "interest rate hike" near each other, and to place the two kinds of "bank" far apart. The vectors are that knowledge, applied to your text.

Two consequences follow for the design, and both are already in the spec. The question and the chunks must be embedded by the same model, since different models produce incompatible coordinate systems, which is why the model id is pinned and a change would mean re-embedding everything. And the model has a 512-token input limit, which is why the chunker caps chunks at 480 tokens: text past the limit is silently cut off and would never be found.
```

```text
isnt creating embedding just code / there is no AI (neural network) involved, am I reading too much into the word model
```

### Replied · 2026-09-08 21:59

```text
No, you are reading the word correctly. An embedding model is a neural network, and a fairly large one. `bge-base-en-v1.5` is a transformer with about 110 million learned weights, the same family of architecture as the chat model, just far smaller and trained for a different job.

Where the intuition "it's just code" comes from is real, though. Older embedding methods were closer to that:

- **Bag of words and TF-IDF** count word occurrences. Pure arithmetic, no learning about meaning. "Interest rate hike" and "the Fed raised rates" share zero words, so they get unrelated vectors.
- **word2vec**, from 2013, was the first widely used learned embedding. It is a very shallow network that learns one vector per word from co-occurrence. Meaning emerges, famously "king minus man plus woman is near queen", but every word gets one vector regardless of context, so both banks are the same bank.
- **Transformer embedders** like BGE read the whole passage and produce one vector for it, with each word interpreted in context. That is what makes "the bank was steep" and "the bank raised fees" land in different places.

So what happens inside `embed()` is a forward pass through a neural network: the text is split into tokens, each token becomes an initial vector, twelve layers of attention mix information between tokens, and the result is pooled down to one 768-dimensional vector. No text is generated, which is why it feels less like "AI" than a chatbot does, but the machinery is the same kind.

The practical tell is that it runs on Workers AI at all. If it were plain code, we would run it inside the Worker and never pay for it. It needs a GPU because it is a 110-million-parameter network evaluated per chunk.

Two more things follow from it being a learned model rather than an algorithm. Its notion of similarity is whatever its training data taught it, so two different embedding models put the same sentence in incompatible places, which is why the id is pinned. And it has an input window of 512 tokens, a fixed property of the network, which is why the chunker stops at 480.
```

```text
Dimension is the length of each vector, and it matters in three ways, only one of which is really a choice for us.

**It is a property of the model, not a knob.** `bge-base` emits 768 numbers, `bge-m3` 1,024, OpenAI's large model 3,072. Picking a model picks the dimension. The exception is "Matryoshka" models, trained so the first N numbers form a usable shorter vector, which is why Nemotron lists 384 to 2,048 and Gemini 128 to 3,072. Those let you trade quality for size after the fact; `bge-base` and `bge-m3` do not.

**More dimensions carry more nuance, with fast diminishing returns.** A vector is a compressed description of a passage's meaning. More numbers can separate finer distinctions, but the benefit flattens quickly: Nemotron's own card shows 2,048 dimensions beating 384 by about four points of recall, and most of that gap closes by 768 to 1,024. For 60-second chunks of spoken English, a 768-dimension model from a good family is well past the knee of the curve. The model's training matters far more than its width.

**It sets storage and query cost, and a hard cap.** Vectorize bills on dimensions stored and dimensions queried, and it allows at most 1,536 per vector, so a 3,072-dimension model cannot be used here without truncation. The dimension is also fixed when the index is created. Changing it means a new index and re-embedding everything.

**Sizing for this product.** A realistic ceiling: 30 channels, 100 episodes each, an hour long, chunked to a minute, about 180,000 vectors.

| Dimension | Stored | Storage cost per month on Paid | Queried per month at 1,000 chat questions |
|---|---|---|---|
| 768 | 138M dimensions | about $0.06 | 139M dimensions, about $0.90 |
| 1,024 | 184M | about $0.09 | 185M, about $1.35 |
| 1,536 | 276M | about $0.13 | 278M, about $2.30 |

Cost is not the deciding factor at any of these. The free plan's 5M stored dimensions is exceeded within the first few dozen episodes on any model, so Vectorize is one more reason M3 assumes Workers Paid.

**The right choice: 768, via `bge-base-en-v1.5`.** English-only content, chunks under 512 tokens, a smaller index that queries faster, and a model that has been stable since 2023. The one reason to go to 1,024 is `bge-m3`, and only if you expect non-English channels, because that model's real advantage is multilingual retrieval rather than its extra dimensions. Both stay under the 1,536 cap with room to spare, and both are Cloudflare-hosted, so neither reopens the rules discussion.

If you take 768, the one-time setup in AGENTS.md is already correct: `--dimensions=768 --metric=cosine`.
```
