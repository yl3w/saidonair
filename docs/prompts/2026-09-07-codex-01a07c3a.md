````text
We have enough decisions to define the schema. I recommend **one shared Registry Durable Object and one User Durable Object per normalized email**.

The Registry owns channels, episodes, shared summaries, and approval requests. Each User DO owns that user’s follows, read status, preferences, and chats. Transcript chunks and embeddings live once in Vectorize.

Each DO has its own SQLite database, so relationships across DOs are application-enforced references; local relationships can use foreign keys and transactions. [Cloudflare SQLite storage documentation](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)

The following is the proposed schema. No repository files have been changed.

**Schema conventions:** IDs are `TEXT`; timestamps are `INTEGER` Unix milliseconds. Every table has `created_at`. Fields marked `?` are nullable. JSON fields are validated JSON stored as `TEXT`.

The shared Registry DO would contain these tables:

| Table | Columns beyond `created_at` | Keys and purpose |
|---|---|---|
| `global_users` | `email`, `last_seen_at` | PK `email`; normalized identity |
| `channels` | `channel_id`, `title`, `canonical_url`, `status`, `initial_import_count DEFAULT 5`, `failure_code?`, `failure_detail?`, `available_at?`, `last_checked_at?`, `last_ingested_at?`, `deleted_at?`, `lifecycle_version DEFAULT 1`, `updated_at` | PK `channel_id`; canonical YouTube `UC…` ID ensures one catalog entry |
| `channel_requests` | `request_id`, `user_email`, `youtube_channel_id`, `submitted_url`, `status`, `reviewed_at?`, `reviewed_by_email?`, `owner_explanation?`, `approved_channel_id?`, `auto_follow_completed_at?`, `updated_at` | PK `request_id`; unique `(user_email, youtube_channel_id)`; preserves requester and review outcome |
| `episodes` | `video_id`, `channel_id`, `title`, `published_at`, `status`, `attempt_count DEFAULT 0`, `failure_code?`, `failure_detail?`, `transcript_checked_at?`, `chunk_count?`, `vectorized_at?`, `processed_at?`, `updated_at` | PK `video_id`; FK `channel_id → channels`; one record per episode, including episodes without transcripts |
| `episode_summaries` | `video_id`, `format`, `executive_summary?`, `takeaways_json?`, `topic_tags_json?`, `raw_text?`, `related_video_ids_json`, `model`, `prompt_version` | PK/FK `video_id → episodes`; one shared summary per episode |
| `ingestion_runs` | `run_id`, `channel_id`, `workflow_id`, `kind`, `status`, `lifecycle_version`, `episode_limit?`, `started_at?`, `finished_at?`, `failure_code?`, `failure_detail?` | PK `run_id`; unique `workflow_id`; records initial, scheduled, and owner-triggered runs |
| `ingestion_run_episodes` | `run_id`, `video_id`, `status`, `failure_code?`, `started_at?`, `finished_at?` | Composite PK `(run_id, video_id)`; local FKs to runs and episodes; records the exact attempted batch and its outcomes |

Approval creates or reuses a `channels` row. Before approval, `channel_requests.youtube_channel_id` identifies the requested YouTube channel without creating an approved catalog entry. Multiple requesters therefore produce separate requests but share one channel and ingestion pipeline.

The per-user DO would contain:

| Table | Columns beyond `created_at` | Keys and purpose |
|---|---|---|
| `channel_follows` | `channel_id`, `followed_at`, `unfollowed_at?`, `origin`, `origin_request_id?`, `updated_at` | PK `channel_id`; retained after unfollow; `origin = manual \| request` |
| `summary_reads` | `video_id`, `read_at` | PK `video_id`; absence means unread |
| `chats` | `chat_id`, `title?`, `updated_at` | PK `chat_id`; a user can have zero or more chats; retain all |
| `chat_messages` | `message_id`, `chat_id`, `sequence_number`, `role`, `content`, `status`, `failure_code?`, `reply_to_message_id?`, `channel_id?`, `updated_at` | PK `message_id`; FK to chat; unique `(chat_id, sequence_number)`; optional legacy `channel_id` stays null for global chat |
| `chat_message_sources` | `source_id`, `message_id`, `position`, `video_id`, `channel_id`, `video_title`, `channel_title`, `start_sec` | PK `source_id`; FK to message; unique `(message_id, position)`; citation snapshots survive catalog changes |
| `user_preferences` | `id`, `system_rules`, `updated_at` | Singleton PK constrained to `id = 'default'`; affects chat answers only |

User tables do not need an email column: the User DO’s identity supplies ownership. `channel_id` and `video_id` references back to the Registry are validated through its methods.

A chat has **no channel membership table**. Its retrieval scope comes from current follows every time someone sends a message. Conversation history remains separate for each chat.

The important state rules are:

| Entity | Allowed states | Transition rules |
|---|---|---|
| Channel request | `pending`, `approved`, `rejected` | Owner decides; rejection may include an explanation |
| Channel | `pending`, `available`, `failed` | First fully processed episode makes it available; owner alone resets `failed → pending` |
| Episode | `pending`, `processing`, `processed`, `no_transcript`, `failed` | Missing captions are distinct from technical failures |
| Ingestion run | `queued`, `running`, `completed`, `failed`, `cancelled` | At most one queued/running run per channel |
| Run episode | `pending`, `processing`, `processed`, `no_transcript`, `failed`, `skipped` | Preserves that run’s outcome even if a later retry succeeds |
| Summary format | `structured`, `raw_fallback` | Retains the existing flagged fallback for invalid model JSON |
| Message | `pending`, `completed`, `failed` | Allows a failed reply to remain visible without losing the user’s message |

A channel becomes `available` when an episode has its complete vector set and stored summary, including an accepted flagged fallback. Later episode failures leave an available channel available.

For an initial import with no processed episodes, proposed failure codes are:

- `NO_TRANSCRIPTS`: every attempted episode definitively lacked captions.
- `NO_EPISODES`: the feed contained no episodes to attempt.
- `INITIAL_IMPORT_FAILED`: processing failed, including mixed technical failures and missing captions.

Failure is decided after the selected batch finishes its attempts. Failed channels receive no scheduled ingestion until the owner resets them to `pending`. Owner retry attempts the latest configured number of episodes, reusing completed work and allowing unsuccessful episodes to be attempted again.

Deletion is represented independently by `deleted_at`, preserving the channel’s processing state. Restoration clears it; previous active follows regain access once the channel is available.

Automatic following needs this specific behavior:

1. Approval and channel availability make a request eligible for automatic following.
2. The User DO inserts a follow **only if no follow record exists**.
3. Existing active or unfollowed records are preserved.
4. After the User DO acknowledges the operation, the Registry sets `auto_follow_completed_at`.

An interrupted handoff can safely repeat. Retaining the unfollowed row prevents a delayed delivery from following the channel again. Request approval itself stays `approved` even if ingestion fails; the request screen combines approval status with channel processing status.

For shared retrieval, use an explicit namespace such as **`shared-catalog`**, with the existing vector IDs `${videoId}:${chunkIndex}`. Metadata retains:

```text
videoId, channelId, channelTitle, title,
startSec, endSec, text, publishedAt
```

Every message computes:

```text
eligible channels =
  active user follows
  ∩ available catalog channels
  ∩ channels without deleted_at
```

Then query that namespace with a `channelId` inclusion filter. Vectorize applies metadata filtering before selecting results and supports `$in`; large channel lists must be split into filters below its size limit and their results merged by score. [Cloudflare metadata filtering documentation](https://developers.cloudflare.com/vectorize/reference/metadata-filtering/)

Before using retrieved chunks, validate their episodes are processed and their channels remain eligible. Partial ingestion must not expose unfinished episodes. Earlier conversation history and its citations remain usable, as agreed.

If the eligible set is empty, store a normal assistant response:

> Chat requires following at least one available channel.

Skip AI and Vectorize calls for that response. Chats remain accessible and messages can still be submitted.

Unread status is user-specific: existing summaries begin unread on first follow, and only summaries actually returned by the digest or channel feed receive `summary_reads` records. Unfollow and restoration preserve those records. Shared summary cross-references should also be filtered to eligible channels when displayed.

The main indexes and integrity constraints should be:

- `channels(status, deleted_at)` for catalog and ingestion selection.
- `channel_requests(user_email, created_at)` and `(approved_channel_id, status, auto_follow_completed_at)` for request views and pending automatic follows.
- `episodes(channel_id, status, published_at)` for feeds and processing.
- `ingestion_runs(channel_id, created_at)`, plus a partial unique index allowing only one queued/running run per channel.
- `channel_follows(unfollowed_at)` for current follows.
- `chats(updated_at)` and unique `chat_messages(chat_id, sequence_number)` for conversation lists and ordering.
- `CHECK` constraints for state values, positive import counts, nonnegative counts/timestamps, and required failure codes when a channel is failed.

Channel deletion and owner retry increment `lifecycle_version`. Workflow writes must match that version, preventing an older run from changing channel state after deletion or restart.

This design replaces the existing per-user ingestion, email Vectorize namespaces, shared-summary `read_at`, and single-chat assumptions in `AGENTS.md` and the PRD. Cron timing remains `TODO(owner)`; no additional product decisions are needed to turn this schema into a design document and migrations.
````
