```text
Partly. There are two separate things going on, and only one of them is about null.

**The main regression is about the empty string, not null.** An empty string is a present, valid string value. Zod's `.optional()` never sees it as "absent" because it is not undefined. It flows into `.trim()` and then `.min(1)`, which fails. Whitespace-only input trims to empty and fails the same way. No amount of optional or nullable handling changes that. Something has to decide that an empty string means "not provided", and the old parser made that decision explicitly. The Zod chain never does.

**Null is a second, smaller loss.** In Zod, undefined and null are different types. `.optional()` accepts undefined or a missing key. `.nullable()` accepts null. `.nullish()` accepts both. The schema only says `.optional()`, so `{"explanation": null}` is a type error, "expected string, received null". The old parser accepted null as absent.

**Why I did not suggest `.nullish()` for the null half.** It would accept null, but the inferred output type becomes `string | null | undefined`. The Registry input types and the web client types are `string | undefined`, so you would be touching signatures and adding null checks downstream for what is really an input-normalisation concern. The preprocess helper collapses null, empty, and whitespace into undefined before the string schema runs. The output type stays `string | undefined`, and the generated OpenAPI document stays identical to today.

So: null is a real part of the gap, but the reviewer's headline case, `{"explanation":""}`, fails for a reason that has nothing to do with null. It fails because an empty string is a string.
```

```text
## Item 2: a discarded digest request still consumes NEW markers

**Verdict: fix it. It is real, and the fix is deleting one line.**

**Why the reviewer is right.** After a follow or unfollow, the three reloads are called back to back. Preact batches their state bumps into a single render. In that render the lists still read "ready" because their "loading" transition happens in effects, after render. So the digest's `enabled` flag is still true, its tick has changed, and its effect fires a request immediately. One render later the lists flip to loading, `enabled` goes false, and the hook drops that request's result. But the API has already recorded read receipts for everything it returned. The receipt is recorded server side before the response is sent. When the lists finish and the real digest request runs, those items come back with `wasUnread` false.

**The user-visible symptom.** You follow a channel, its summaries appear in the digest, and none of them carry the NEW marker. The spec says the marker is the only trace the user gets of what they had not seen, so losing it on exactly the action that brings new items in is a real defect.

**Why the fix is tiny.** The load hook already re-runs its effect when `enabled` changes, and it already refetches when `enabled` goes from false to true. That is the mechanism the Home screen uses for the initial load order. The reload-lists call alone triggers the whole sequence correctly: lists go loading, the digest's `enabled` flips false and it shows "Loading…" without fetching, both lists finish, `enabled` flips true, and one digest request fires. The explicit `reloadDigest` in `reloadAll` is the only thing that breaks that sequence.

**How to do it.**

1. In `apps/web/src/screens/Home.tsx`, remove the digest reload from the after-action callback so it reloads only the two lists. Rename the callback to say what it now does, and add a two-line comment stating that the digest follows through the `enabled` flag once both lists are ready, and why an explicit digest reload here would fire early and burn receipts.
2. Keep `reloadDigest` itself. The Digest component's Retry button still needs it, and that path is safe because the lists are already ready when a user can click Retry.
3. Trace the sequence once by hand before committing, since there is no web test runner. The question to answer is: at each render after a follow, what are the digest's `enabled` and tick, and does the effect fetch? You should find exactly one fetch, after both lists are ready.
4. Run `pnpm check`, then verify in the browser: follow a channel that has unread summaries, watch the network panel, and confirm one digest request after the two list requests, with NEW markers on the new channel's items.

**What not to do.** Do not build sequencing into the hook, for example by making reload return a promise so the caller can await the lists and then reload the digest. The dependency already exists in the `enabled` flag, and a second mechanism for the same ordering is how the next drift happens.

**One thing to notice for the future.** This bug is a general property of the digest endpoint: any request that runs is a read, whether or not the result is displayed. Every place that could issue a speculative or duplicated digest request has this hazard. Today Home is the only caller, so removing the early reload closes it.
```
