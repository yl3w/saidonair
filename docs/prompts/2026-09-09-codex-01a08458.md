Let’s start with **finding 1: a channel can get stuck before the user receives any content.**

Imagine this experience:

1. You request a channel.
2. The owner approves it.
3. You see that the channel is importing and expect summaries to appear.
4. The pipeline discovers that the recent videos don’t have captions yet.

Waiting is reasonable here—the spec intentionally allows captions time to arrive. The problem is **what happens after that wait begins**.

The documents currently describe two incompatible outcomes: the episodes should wait and be checked again, but an initial import with no successful episodes should fail the channel. Meanwhile, the scheduled process only checks channels that are already available.

From your perspective, a temporary delay can therefore become permanent. You either see an import failure that needs owner intervention, or keep waiting for an import that has no automatic path forward.

Credit exhaustion creates a similar experience: the channel stays pending, but replenishing credits does not make the planned scheduler pick it up.

**The experience I’d recommend:** distinguish waiting from failure, even if those are explanations within the existing state model:

- **Waiting for captions:** “Approved. Waiting for captions; we’ll check again automatically.”
- **Waiting for credits:** “Approved. Import is paused until transcript credits are available.”
- **Failed:** “We couldn’t import this channel. The owner needs to retry.”

Each waiting message must correspond to a real automatic recovery path. The user should not need to understand ingestion runs or ask the owner to repair a temporary delay.

**The decision for you:** should approved channels waiting for captions or credits resume automatically, without another owner action?
