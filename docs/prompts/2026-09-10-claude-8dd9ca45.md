```text
I have everything I need from the docs, routes, Registry stores, and web screens. Here is the explanation.

Channels are the shared unit of the product: one YouTube channel, identified by its canonical `UC…` id, sitting in a single global catalog that the owner curates. Each channel is ingested and summarised once, and every user reads the same episodes and summaries. Roles differ in who puts a channel into the catalog and changes its state versus who subscribes to it.

Every channel has a processing state of pending, available, or failed, plus an independent soft-delete flag. Only a channel that is available and not deleted is visible or followable for users. Pending means the initial import has not yet produced a fully processed episode. The first processed episode flips it to available. Failed means the import ended with no usable episode, with a reason such as no captions, an empty feed, or a technical failure.

## What a user can do

- **Browse the catalog.** Home lists available channels they don't follow yet, with the processed episode count and a Follow button.
- **Follow and unfollow.** Following only works on an available, non-deleted channel, and existing summaries start unread. Unfollowing leaves a tombstone so the channel drops out of their digest, and they can refollow later.
- **Read a channel.** The channel page shows episodes newest first. Followers see the shared summaries, and viewing them records a private read receipt. Non-followers see titles and a Follow control, and a pending, failed, or deleted channel reads as not available.
- **See their followed list.** Each followed channel shows processed count, unread count, last ingestion time, and Unfollow. If the owner deletes a channel, the follow stays listed and unlinked as removed by the owner.
- **Request a missing channel.** They paste a `UC…` id or a `/channel/UC…` URL. Handles and other URLs are rejected with instructions on where to copy the id, and the API verifies the id against YouTube's RSS feed and stores the feed title. If the channel is already available they get "Already in the catalog" with a Follow button instead of a request.
- **One request per user per channel.** Pending, failed, and deleted channels can still be requested. Several users may request the same channel.
- **Track their own requests.** Each shows one phrase derived from the request plus the channel's current state: waiting for review, declined with the owner's note, approved and importing, import failed with the reason, about to be followed, following, or removed by the owner. The list polls while a request is in flight.
- **Be followed automatically on approval.** By spec, approval follows the requester right away, even before the channel is available. Content appears only once it is processed.
- **Downstream effects.** Digest and chat use only the channels the user follows that are available and not deleted. Users never see other users' requests, follower counts, or any owner data.

## What the owner can do

The owner is whoever holds the owner role in the Registry, seeded from the `OWNER_EMAIL` secret. They get everything above plus catalog management. The Registry re-checks the role on every owner action, so the client's role only controls what renders.

- **Review requests.** The Owner page lists pending requests oldest first with requester, channel title, id linked to YouTube, the id's current catalog state, and how many others requested it. Approve takes an optional title override, import count, and note. Reject takes an optional note the requester sees.
- **See the review history.** Reviewed requests collapse with reviewer, time, note, and whether the automatic follow was delivered.
- **Approve creates or reuses one channel.** If the id is new, approval creates a pending channel with the request's stored title unless overridden and starts the initial import. If the channel exists, approval reuses it, so several requesters share one channel and one pipeline. Approval is refused while the channel is deleted, and the owner must restore it first.
- **Add a channel directly.** The Add form takes an id, optional title, and import count, defaulting to the five most recent episodes. The id is verified against its feed and the feed title is used unless given. An id already in the catalog, including a deleted one, is refused.
- **See every channel in every state.** A health strip summarises the catalog. A Needs attention section lists failed channels with a humanised reason and latest run, plus pending channels with no run. The All channels table shows state, processed versus tracked episodes, no-caption and failed counts, last ingested, latest run, requester count, and actions.
- **Requester count replaces follower count.** Follows are private to each user's Durable Object, so the owner never sees who follows what.
- **Retry.** Resets a failed, non-deleted channel to pending, clears the failure, bumps the lifecycle version so stale runs are fenced out, and starts a fresh import that reuses completed work.
- **Delete.** Soft delete, confirmed once. Ingestion stops and the channel drops out of every user's catalog, digest, and chat, while follows, read receipts, episodes, summaries, and vectors are kept.
- **Restore.** Clears the deletion. Users still following regain access once the channel is available, users who unfollowed stay unfollowed, and a failed channel is not retried by restoring.
- **Inspect one channel.** The owner detail page shows the management block, the episodes with processing detail, the ingestion runs with per-episode outcomes, and every user's requests for that id. It never shows any user's read or chat activity.

## Specified but not built yet

The docs describe the full lifecycle, but some pieces are still ahead of the code on `main`:

- **Ingestion itself.** Add, approve, and retry only log an ingestion request today. No Workflow or cron exists, so a channel created now stays pending until the M3 ingestion work lands.
- **Automatic follow delivery.** The User DO can accept an automatic follow and that is tested, but approval doesn't call it yet. It is step 7 of the M3 plan.
- **Waiting states and episode retry.** The uncommitted spec edits in your working tree add a channel-level waiting reason for captions, live videos, or transcript credits, a non-English failure code, per-episode owner retry, and richer followed-list rows for pending and failed follows. None of these are in the schema, API, or UI yet.

I can publish this as a shareable reference page if that would be useful.
```

```text
**Verdict:** the direction is right and the timing is good. The proposal moves state to where the information actually lives, on episodes, and makes the channel a plain approval container. Today's design already behaves that way in disguise, since available is absorbing and every later problem is an episode problem. Because the M3 ingestion work is not built yet, this removes more unbuilt work than it adds. It holds together only if three gaps are closed: what rejection means, how deliberate skips differ from real failures, and how the owner stops a hopeless channel from consuming transcript credits forever.

## Point by point

- **(a) Two channel statuses, available on approval.** Sound. It deletes the channel retry route, four channel failure codes, the channel-level failure classification in the M3 spec, and the channel waiting code. Two costs: "available" no longer promises readable content, which item (d) must compensate for, and the proposal is silently three states, because a declined request needs a home. Consider naming them requested and approved, since "available" on a channel with zero summaries will read as a bug.
- **(b) Requests create a pending channel.** Fine, and it collapses the request list and the catalog into one entity. The feed check and title fetch already happen at request time, so the data is there. It forces the rejection decision: I recommend reject soft-deletes the never-approved channel and keeps the explanation on the request, and a fresh request for such a channel reopens it. Approved-then-deleted channels stay owner-restore-only, so the 2026-09-07 "restore it first" rule survives where it matters.
- **(c) Follow anything.** The big win, and larger than stated. If a requester follows the pending channel at request time, the automatic-follow handoff disappears entirely: the User DO method, the completion timestamp, the background sweep, the "never reverse an unfollow" retry rules, and M3 step 7. Two caveats. "Anything" should still exclude deleted channels. And chat eligibility stays exactly as hard rule 3 requires, followed and approved and not deleted, because a pending channel has no vectors anyway.
- **(d) Episode metadata on the channel.** Cheap and necessary. The owner-only management block already carries the counts, and the count query already runs for every list. Expose tracked, available, pending, failed, and skipped counts plus last ingested to everyone, so a follower can read "approved, 0 of 5 summarised yet" instead of an empty digest.
- **(e) Episode statuses pending, available, failed.** Right shape, wrong definition of failed. Most real failures are transcript failures, not summarisation failures: no captions, non-English, too short, live, provider credits. The 2026-09-08 decision to keep "no captions" distinct from technical failure must survive, and "no captions yet" on a video under two days old is a pending episode with a wait reason, not a failure. Dropping the processing status is defensible because the run table carries in-progress state and vector ids are deterministic.
- **(f) Owner reviews and retries failed episodes.** Already in the uncommitted spec as the per-episode retry route, so this consolidates rather than adds. The risk is volume: a channel that never has captions produces a failed episode for every upload, forever, and the attention list scales with videos rather than channels. Item (g) is the fix if it is applied automatically as well as manually.
- **(g) Owner can skip a failed episode.** Good, and it should do more work than proposed. Let the system skip deterministic outcomes on its own, with a reason: too short, non-English, no captions after the waiting window, live. Reserve failed for technical and provider errors where a retry can help, and make skipped reversible by owner retry. Then the owner's queue only holds things worth a click.

## What it removes and what it adds

| Removed or avoided | Added |
|---|---|
| Channel retry route and Registry method | Request creates the channel row, in the same Registry transaction |
| Channel failure codes and their web copy | A rejection rule and its representation |
| Channel-level failure classification and recovery rules in the M3 spec | Episode skipped status, skip reason, owner skip route |
| Channel waiting code from the working-tree spec | Episode wait reason on pending episodes |
| Auto-follow handoff across both Durable Objects and its sweep | A light requester record so the owner queue still shows who asked |
| Follow eligibility guard and the "already available, follow instead" 409 path | Public episode counts on every channel representation |
| Seven request outcomes down to about four | A channel-level pause, if you accept condition 3 below |
| Three Home subsections down to two | |

Net for the code on main: a moderate refactor of the Registry stores, three route files, the outcome derivation, and the owner screens, plus a large test rewrite. Net for the unbuilt M3 work: clearly smaller. The M3 spec and plan on the feature branch would need revising before anyone starts them.

## Conditions before adopting

1. **Decide rejection.** Without it, (a) is a third state in disguise and (b) has no path for "no". The soft-delete-and-reopen rule above is the least new machinery.
2. **Split failed from skipped, with automatic skipping.** Otherwise owner attention grows with upload volume, and the 2026-09-08 caption-versus-technical distinction is lost.
3. **Keep a channel-level stop.** Today a failed channel leaves scheduling. Under the proposal every approved channel is fetched every six hours and each new video attempted costs a DownSub credit, with or without captions, out of a monthly budget of two thousand. Delete is the only lever left and it reads as "removed by the owner" to followers. An owner pause flag is small and honest.
4. **Accept two visibility changes.** Pending channels become visible to every user as part of the catalog, so requests are no longer private to the requester. And approving a request no longer creates the channel, so approval becomes a pure status flip with a title and import-count override.
5. **Revisit one earlier decision on purpose.** The rule that technical failures are never retried automatically now puts every transient provider error in front of the owner. With attempt counts already on episodes, retrying a technical failure a few times before surfacing it would cut the queue further. That is the owner's call, not a consequence of the proposal.

Superseded decisions to record if this goes ahead: the 2026-09-07 refusal of requests for available channels, the 2026-09-10 immediate auto-follow rule, and the NON_ENGLISH channel code from 2026-09-08, which becomes an episode skip reason.

I can publish this as a decision page alongside the lifecycle diagram, or fold a "proposed" second diagram into the existing artifact, if you want it in front of the team.
```

```text
**Verdict:** yes to both, with two amendments. A `declined` status removes the last orthogonal axis from the channel, which is exactly what my earlier review flagged as "a third state in disguise". The amendment is to drop the "and pause" half of (a): a declined channel is excluded from scheduling by its status alone, and setting the pause flag as well encodes the same fact twice. And the re-request in (b) should show the decline note and ask once, rather than flip silently.

## As group PM

**It removes a concept users never needed.** Soft delete gave the reader two different messages for what feels like one event: "declined" if the owner said no before anything ran, "removed by the owner" if the owner withdrew it later. One status with the owner's note covers both. Copy can still say "withdrawn" when the channel had been approved, because `approved_at` is set, without a second status.

**Re-request becomes a first-class path instead of a side effect.** Under the current draft a declined channel reopens because someone pasted the id and the route cleared a timestamp. Making it a status transition lets the product be honest about it: paste the id, see "Declined on 3 Sept: 'not English'", choose "Request again". That one confirmation respects the owner's earlier decision and stops well-meaning users from re-asking by accident. It also belongs on the follower's own row in Followed, since they are already following the channel.

**The owner gets fewer verbs.** Approve and Decline work on any channel that is not already in that state, so Restore disappears into Approve and Delete disappears into Decline. The owner page needs Approve, Decline, Pause, Resume, and nothing else at channel level. Declining an approved channel with followers should still confirm once and show the follower count, since it hides summaries for all of them.

**Two product questions to settle.** Whether declined channels appear in the browsable catalog: I would hide them and surface them only on paste and in their followers' lists, so the catalog stays a list of things you can read or wait for. And whether the queue should flag a re-request as "previously declined, twice", which needs a review log rather than the latest-note fields. Not needed now, easy to add later.

**What is lost.** The 2026-09-07 rule that approval must never quietly resurrect removed content becomes moot, because the owner is the one approving and the queue shows the history. Nothing else. Retention is unchanged since nothing is deleted at all.

## As engineer

**It simplifies, and by more than it looks.** The current draft has two statuses and two flags, and the meaning of `deleted_at` depends on the status next to it. Every reader of a channel row has to consider the pair. With a status, the row means one thing:

| | Current draft | With `declined` |
|---|---|---|
| Fields that carry state | `status`, `deleted_at`, `paused_by` | `status`, `paused_by` |
| Real combinations | requested, approved, approved·paused, requested·declined, approved·removed | requested, approved, approved·paused, declined |
| Eligibility for digest and chat | approved and `deleted_at IS NULL` | `status = 'approved'` |
| Catalog listing for users | not deleted | `status IN ('requested', 'approved')` |
| Cron selection | approved, not deleted, not paused | approved, not paused |
| Routes | approve, decline via DELETE, restore, pause, resume | approve, decline, pause, resume |
| Guards that mention deletion | reopen only if requested, restore only if approved, 409 for removed | none |

**Transitions stay about the same in number but live on one axis**, which is what makes them testable: requested to approved, requested to declined, declined to requested by re-request, declined to approved by the owner directly, approved to declined. The fence bump moves from delete to "approved to declined", because that is the only transition that can have a run in flight. Pause is cleared on decline and recomputed on approve from the follower count, so the flag only ever means something on an approved channel.

**Nothing new in the schema.** The status column is text, so the value is a code change. The existing `deleted_at` column stays unused, like the other deprecated columns. The follower record, the auto-pause rule, and the episode machine are untouched.

**Two details to pin down in the spec.** Approve from declined does not start an initial import if the channel has already been approved once; cron simply picks it up again. And `POST /channels` on a declined id should return the channel with its decline note and a `requestAgain` hint rather than flipping it, so the confirmation lives in the client and the flip is an explicit second call, or the same call with a flag.

If you want this adopted, the changes are contained: the channel section and the API table of the spec on the branch, and the channel diagram in the artifact, lose the deleted row entirely. I can make both edits on your word.
```
