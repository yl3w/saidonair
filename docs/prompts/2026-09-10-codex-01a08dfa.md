### Replied · 2026-09-11 12:19

```text
I recommend keeping the components mounted, using a narrowly defined opt-in such as `retainDataOnReload`.

The form draft belongs inside `WaitingRow`. Lifting `mode`, `title`, `count`, `note`, errors, and busy state into `OwnerScreen` would couple the screen to every child form field, require keyed cleanup when channels change status, and make future form changes unnecessarily cross-cutting.

I would refine the loader design:

- Initial loads and dependency changes still transition to `loading`.
- Only an explicit `reload()` retains existing ready data.
- Represent this as `status: "ready"` with `refreshing: true`, rather than introducing a fourth status every consumer must handle.
- If refresh fails, retain the existing data and expose a separate `refreshError`; otherwise the components would unmount again.
- Opt in for Owner’s channel and catalog loads only. Home must preserve its current `ready → loading → ready` transition because that orders the digest request after both lists refresh.
- Disable owner mutation controls while the channel list is refreshing. Otherwise stale Approve/Decline/Pause controls become clickable again before the authoritative state arrives.
- When fresh data arrives, changed rows naturally move or unmount. A successfully applied-but-response-lost approval moves from Waiting to Reviewed, while a genuine failure leaves the form and error intact.

I would name the option `retainDataOnReload`, not `keepData`, because the latter could imply retaining data across dependency changes—which would be dangerous for channel-ID-based loads.

This approach fixes the lifecycle boundary at its source while preserving local component ownership. The state-lifting alternative is workable, but it introduces substantially more plumbing and makes `OwnerScreen` responsible for presentation details it should not own.
```
