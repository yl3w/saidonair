```text
Short answer: it works, and I'd recommend a version of it, but not the pure form. The unit of *execution* can be an episode without making the unit of *bookkeeping* an episode. The schema, the owner screens, and half the spec are built around the channel run, and most of the pain you'd take on comes from abandoning that grouping rather than from per-episode Workflows themselves.

## What you gain

- **Isolation.** A lost or stuck instance blocks one episode, not a channel. Today a lost run holds the channel's only active slot until reconciliation.
- **A simpler Workflow.** The instance is `{ videoId, channelId, lifecycleVersion }` plus steps. Feed fetch, selection, `PROVIDER_LIMIT` early exit, and `not_attempted` bookkeeping all leave the Workflow.
- **Parallelism.** An initial import of five finishes in the time of one episode. Owner retry becomes exactly "create one instance", which is what the spec already wants and currently has no clean way to express.
- **Waits could become self-contained.** An instance that gets "no captions" could `step.sleep` six hours and re-check, up to the 48-hour cutoff, instead of relying on cron re-selection. Workflows allow long sleeps. That removes the trickiest selection rule from the cron. It does mean sleeping instances count as active and reconciliation must not treat them as lost.

## What you lose or must rebuild

- **The feed fetch moves out of a retryable step.** It lands in the approve route or the scheduled handler. Approve becomes network-dependent on YouTube, so you need a rule: approval commits regardless, and a failed feed fetch leaves the channel "approved, never started" until cron or Start. The owner add route already has the feed in hand, so only approve gains a call. Feed failures also lose their home: `FEED_UNAVAILABLE` was a run failure code, and there is no run to carry it.
- **Fan-out with no throttle.** One cron tick launches channels × pending episodes instances that all hit DownSub within seconds. The channel model serialised episodes per channel for free. You'd need jittered start sleeps, waves from the scheduled handler, or a Queue binding, and rate-limit answers must stop counting as episode attempts. Instance concurrency caps also matter here: I recall a low cap on the free plan and a high one on Paid, so the open Workers-plan decision bites this model harder.
- **Credit exhaustion stops nothing.** Today one 403 ends the run. Per episode, every remaining instance still makes its call. Those cost no credits, so the fix is cheap: have cron check `/status` before launching and skip launching while credits are zero.
- **The schema fights the pure form.** The partial unique index allows one queued or running run per channel. One row per episode instance violates it as soon as two episodes are in flight, and dropping an index is not an additive migration, so it needs your approval and a new migration. `episode_limit`, `lastSuccessfulIngestionAt`, `latestRun`, `neverStarted`, and the owner's runs screen with per-episode outcomes all assume the run grouping.
- **More to reconcile.** One status call per open instance per tick instead of one per channel.

## What I'd recommend: keep the run, split the work

Keep `ingestion_runs` as the per-channel batch and make each Workflow instance one episode of that batch.

1. Approval, cron, Start, and owner retry create the run row, fetch the feed, upsert the episode rows, and record the selection, all in the request or scheduled handler. The run is `running` from creation.
2. For every selected episode the handler creates one instance with id `${runId}.${videoId}` and params `{ runId, videoId, channelId, lifecycleVersion }`. The deterministic id means no new column: reconciliation recomputes it.
3. Each instance ends with one fenced Registry write that records its run-episode outcome. The Registry closes the run when no `selected` row remains, with `completed` or `failed` derived from the outcomes. That count-down is atomic inside the Durable Object.
4. Decline from approved marks the active run and its remaining run-episodes cancelled in the same transaction, which also answers the cancel gap from my review.
5. The one-active-run rule keeps its meaning: a new scan for a channel waits until last tick's episodes are done.

This needs no migration, keeps every existing route and screen, keeps fencing and never-started as they are, and still gives you per-episode isolation, parallelism, and a Workflow that is only the pipeline. What it costs is the count-down close, per-instance reconciliation, and a throttle on launch. The plan's Steps 4, 6, 7, and 8 would be rewritten; Steps 1, 2, 3, and 5 are untouched.

If you want the pure form anyway, the decision you'd be making is to drop the one-active-run index and re-point the runs screen, `latestRun`, and never-started at per-episode jobs. That is a bigger spec revision than the hybrid and I don't think it buys anything the hybrid doesn't.
```

````text
Section 3 is about bookkeeping, not about the fence. The fence already exists and already does the important thing. Let me separate the two.

**What the left panel shows.** In the hybrid, the run row is created `running` with one `selected` row per episode. Each instance resolves its own row when it finishes. **Why anything else is needed.** The run row. Nobody can close it:

1. The in-flight instances cannot. The spec says the Workflow "treats the refusal as cancelled and stops", but writing `cancelled` on the run row is itself a fenced write, so the Registry would refuse that too. The spec assigns the job to the one party that cannot do it.
2. The count-down close never fires. B's instance had not started, D's exits without writing, so two rows stay `selected` forever.
3. Reconciliation does not catch it either. It closes runs whose Workflow is missing or failed. A fenced-out instance exits cleanly, so its run looks healthy.

So the run stays `running` indefinitely. That is not cosmetic. The partial unique index allows one queued or running run per channel, and cron selection skips channels with an active run. If you re-approve the channel, it can never be ingested again. The catalog's active-run count is wrong. The runs screen shows a run that never ends. And the spec's own acceptance criterion 3 says the run must read `cancelled`, so this is making the spec's promise implementable rather than adding a requirement.

**The change is two statements** inside the `declineChannel` transaction that already bumps the fence:

```sql
UPDATE ingestion_runs SET status = 'cancelled', finished_at = ?
 WHERE channel_id = ? AND status IN ('queued', 'running');

UPDATE ingestion_run_episodes SET status = 'not_attempted'
 WHERE run_id = ? AND status = 'selected';
```

Doing it there rather than anywhere else has three properties. It is atomic with the fence bump, so there is no moment where the channel is declined but still shows an active run. It is the one write that legitimately passes the fence, because it is the write that moves the fence. And it covers every case, including a run that was still `queued` and an instance that died before writing anything.

The in-flight instances keep running until their next Registry call, get refused, and exit. They may spend one transcript credit or one AI call in that window. Nothing they produce is stored, and nothing else needs to be done.

This applies equally to the spec's channel-run model, by the way. One Workflow or many, the run row has the same problem. The hybrid did not create it, it just made it visible, because the count-down close depends on every `selected` row being resolved by someone.
````

### Replied · 2026-09-11 13:40

```text
**What it is.** `lifecycle_version` is a counter on the channel row, starting at 1. Exactly one transition bumps it: declining a channel that was approved. When a run is created it copies the channel's current number onto the run row. The spec then says every write a run makes must present that number, and the Registry refuses the write if the channel's number has moved on. In distributed-systems terms it is a fencing token: a stale worker holding an old token cannot write once the world has moved past it.

**Why it exists.** The scenario is decline, then re-approve, while an old run is still alive. A plain "is the channel approved?" check on every write is not enough, because after the re-approval the answer is yes again, and the old run would carry on publishing under the new approval. The version distinguishes the approval the run started under from the one that now holds.

It was designed for the earlier channel model, when runs also wrote channel state: import status, failure codes, and a channel could be deleted and restored. A stale run resurrecting a channel's import state after a restore was a real hazard, and the PRD's wording still reflects that: "cannot publish stale state after a withdrawal". On 2026-09-10 runs stopped touching channels at all. The only things a run writes now are episodes, run-episodes, and two timestamps on the channel. The threat the version guards against shrank to "an old run publishes an episode into a channel the owner has since re-approved", which is content the owner wants anyway.

**The simplification: fence on the run row, not on the channel.** Every write from an instance already names its run. Make the rule: a write is accepted only while that run is `queued` or `running`. Decline cancels the channel's active run, as section 3 already requires. That gives you:

- **Decline.** The run is `cancelled`; every later write from it is refused. Same as before.
- **Decline then re-approve.** The old run stays `cancelled`; a new run starts on the next cron or Start. The old instances are refused and exit. No counter needed to tell the two approvals apart, because the run row already belongs to exactly one of them.
- **Reconciliation.** A run closed as `WORKFLOW_LOST` whose instance turns out to be alive is also refused. The version fence never covered this case, since the channel's version had not changed. So the run-status fence is strictly stronger.
- **The cancel paradox disappears.** Section 3's problem was that cancelling was itself a fenced write. Now the decline closes the run and instances check the run, so nothing is self-referential.

The check is one primary-key lookup inside the Durable Object, and it removes the copying, comparing, and testing of version numbers everywhere. You can keep a defensive "channel is approved" check on the write as well, but with decline cancelling runs it is implied.

**What would change.** The two `lifecycle_version` columns stay, since the schema is frozen and additive-only; the Registry can keep bumping the channel's on decline as a harmless audit count or leave it at 1. The `lifecycleVersion` fields on the channel management and run shapes, and the "lifecycle v1" in the owner detail header, either go or become informational. The M3 spec's fencing row, the PRD's §4.2 sentence, and the AGENTS.md lines that say run writes must match the version would be rewritten to say run writes require an open run. That is an owner decision, so I have not touched anything.
```

```text
## The picture today

The Registry is one Durable Object that holds the catalog in SQLite: channels, episodes, and ingestion runs. A run is one pass over one channel, recorded as a row in `ingestion_runs` plus one row per episode it decided to work on. A Workflow is Cloudflare's durable job runner: you write a function as a series of steps, and each step retries on its own if it fails. Today none of the ingestion code exists. The spec says to build it as one Workflow per channel run, which fetches the feed, picks episodes, and then processes them one after another inside that single job.

## Change 1: one Workflow per episode, but keep the run row

The run stays as the unit of bookkeeping. The Workflow becomes the unit of execution, and it handles exactly one episode.

- **The handler does the setup.** When a channel is first approved, when cron fires, or when the owner clicks Start or Retry, ordinary Worker code fetches the RSS feed, writes the run and its selected episodes to the Registry in one transaction, and then creates one Workflow instance per selected episode.
- **Each instance is small.** Its parameters are the run id, the video id, and the channel id. Its steps are transcript, classify, embed, upsert, verify, summarize, related, publish. It never fetches the feed, never picks episodes, and never touches channel status.
- **Instance ids are predictable.** An instance is named `runId.videoId`, so reconciliation can compute the name later without storing it.
- **Three writes back.** An instance can only call `markTranscript`, `completeEpisode`, or `failEpisode` on the Registry. Each updates the episode and its run-episode row together.
- **The run closes itself.** When a write resolves the last run-episode row that is still `selected`, the Registry marks the run completed and stamps the channel's timestamps. Waiting for captions counts as a normal completion.

Why: one lost or stuck job blocks one episode instead of a whole channel, episodes process in parallel, the Workflow code is only the pipeline, and no migration is needed because the existing tables already fit. The cost is one throttle we still have to design, so that a cron tick does not hit DownSub with every pending episode at the same second.

## Change 2: declining a channel stops nothing that is already running

The spec carries a fencing token called `lifecycle_version`. Declining an approved channel bumps it, every write from a run has to present the number it started with, and a mismatch is refused. The idea was to stop an old run from writing stale channel state after the owner withdrew the channel.

That danger belonged to an older design where runs wrote channel status. Runs no longer do that. Today a run can only produce episode summaries and vectors, which are hidden from readers as soon as the channel is declined, kept anyway by policy, and exactly what the next run would produce if the channel is approved again. Pause already lets a running run finish. So:

- **Decline becomes a status change and nothing more.** No version bump, no cancelling runs, no `cancelled` status to explain. A run in flight finishes; its summaries are invisible until re-approval.
- **The version columns stay but go quiet.** The schema is frozen, so the columns remain. Nothing reads or compares them. The `lifecycleVersion` fields leave the API and the owner detail header.
- **One cheap check remains, for a different reason.** Before writing, an instance confirms its run is still open. That protects against reconciliation closing a run whose job was in fact alive and cron starting a duplicate. It has nothing to do with decline.

This reverses a decision recorded on 2026-09-10 in AGENTS.md, the PRD, and two specs, so it is explicitly yours to confirm.

## Change 3: gaps in the spec to fill before building

- **Define "new feed entry"** as untracked and published after the channel's first approval. Otherwise the first cron after approval imports the ten older videos the initial import deliberately skipped, at one credit each.
- **Give the owner-retry run its episode.** Pre-insert the run-episode row at creation so the one instance knows which video it owns.
- **Do not charge account problems to episodes.** A bad DownSub key or a rate limit ends the run and leaves episodes pending with no attempt counted, instead of marking every episode failed after three cron cycles.
- **Retry the vector check before counting an attempt.** Vectorize applies writes asynchronously, so an immediate read can miss vectors that are on their way.
- **Pick how related episodes are found.** Either each embed step returns a running sum for a centroid, or the summary text is embedded and queried.
- **Smaller fixes.** Feed failures are run-level only. Cap transcript size against the step-result limit. Break digest ties by publication date. Define the two channel timestamps. Put a timeout on the credits call so the owner's Home never waits on DownSub. Teach the test feed fake to emit entries. Check credits before launching so an exhausted account launches nothing.

## What does not change

The schema and its constraints, every existing route and screen, the episode state machine with its wait, skip, and three-attempt rules, the transcript seam, chunking, the AI and Vectorize wrappers, the six-hour cron, and the rule that a channel nobody follows is paused while its first import still runs. Plan Steps 1, 2, 3, and 5 are untouched; Steps 4, 6, 7, and 8 get rewritten.
```

```text
**Two ledgers that cannot be updated together.** The Registry's SQLite is one ledger: it says a run is `running` and lists which episodes are `selected`. Cloudflare Workflows is the other: it is where the instances actually execute. There is no transaction spanning both. 1. The run row is written, then `create()` throws for an episode because of a network error or a platform limit. The Registry believes that episode is in flight. Nothing is running.
2. An instance exhausts its step retries, say DownSub was down for an hour, and errors out. Workflows records it as errored. It never made its final Registry write, so the Registry still says `selected`.
```

````text
## How an instance runs

A Workflow instance is one call of `run(event, step)`. Inside it, every `step.do(name, config, fn)` is a checkpoint: Cloudflare runs `fn`, saves its return value, and if the machine dies or the code crashes later, it replays `run` from the top, and every step that already finished returns its saved value instantly instead of running again. Each step also has its own retry policy. If a step's retries are exhausted, `step.do` throws inside `run`. If that exception escapes `run`, the instance ends as **errored** and nothing else in it executes.

That last sentence is the whole issue. An instance that dies without telling the Registry leaves its run-episode `selected`, and the only thing that ever notices is the reconciliation sweep an hour or more later, which labels it `WORKFLOW_LOST`.

## The instance's steps

For one episode, in order:

1. **stagger**: sleep `startDelaySec`. No result.
2. **transcript**: call `source.fetch(videoId)`. Either returns a `TranscriptResult` (segments, duration, live flag, caption status) or throws a `TranscriptError` whose reason is one of `UNPLAYABLE`, `PROVIDER_AUTH`, `PROVIDER_LIMIT`, `PROVIDER_RATE_LIMIT`, `PROVIDER_HTTP`, `PROVIDER_PARSE`. Some reasons are marked non-retryable and throw at once; the rest are retried by the step and thrown only after the retries are spent.
3. **classify**: the first Registry write, `markTranscript`. The Registry applies the rules that live there: English captions mean continue; no captions on a fresh video means wait; a short video means skip; a provider error means a technical attempt, or an account-level stop. Anything but "continue" ends the instance here.
4. **embed** and **upsert**, one pair per batch of chunks.
5. **verify**: `getByIds` until every vector is present.
6. **summarize** per section, then **reduce** if there was more than one section, then **related**.
7. **publish**: the second Registry write, `completeEpisode`.
8. If any step in 4 to 7 gives up after its retries: the third write, `failEpisode`.

## Where the plan is wrong

The plan says: wrap "everything after classify" in a try/catch and call `failEpisode` from the catch. Step 2 sits outside that block. So when DownSub answers 500 three times, the transcript step throws `PROVIDER_HTTP`, nothing catches it, `run` throws, and the instance errors out silently. The Registry never gets the `markTranscript(technical, PROVIDER_HTTP)` it needed. The episode's attempt count does not move, and an hour later the sweep records `WORKFLOW_LOST`, which is the wrong code for the wrong reason. The same happens for a wrong key, for exhausted credits, and for an unplayable video, each of which has a precise outcome the Registry knows how to record.

The rules for those outcomes deliberately live in `markTranscript`, not in the instance. So the fix is not to move the rules; it is to make sure every way the transcript step can end reaches that write.

## The change

Two catch regions, and the write chosen by the stage that failed:

```ts
async run(event, step) {
  const { runId, videoId, channelId, startDelaySec } = event.payload;
  await step.sleep("stagger", `${startDelaySec} seconds`);

  // Stage 1: everything about the transcript ends in markTranscript.
  let outcome: TranscriptOutcome;
  try {
    const result = await step.do("transcript", TRANSCRIPT_RETRIES, () => source.fetch(videoId));
    outcome = classifyResult(result, publishedAt, Date.now());  // captions | waiting | skipped | deterministic
  } catch (error) {
    outcome = classifyError(error);                             // technical | accountLevel | waiting | skipped
  }
  const decision = await step.do("classify", () => registry.markTranscript(runId, videoId, outcome));
  if (decision !== "continue") return;

  // Stage 2: everything after that ends in completeEpisode or failEpisode.
  try {
    // embed, upsert, verify, summarize, reduce, related, publish
  } catch (error) {
    if (isRefusedWrite(error)) return;                          // the run was closed under us; log and exit
    await step.do("fail", () => registry.failEpisode(runId, videoId, codeOf(error), detailOf(error)));
  }
}
```

Three details make this hold up:

- **The Registry writes are steps too.** A replay after a crash must not perform `markTranscript` twice, so the write sits inside `step.do` and its saved result is reused.
- **Carry the reason in the message.** An error thrown inside a step reaches the catch after retries, but its class and custom fields may not survive the engine's serialisation. `TranscriptError` should put its reason at the front of the message, exactly as `DomainError` already does with its code, and `classifyError` recovers it the way `domainErrorCode` does.
- **A refused write is not a failure.** If the Registry answers `INVALID_STATE` because the run was closed, the instance logs and exits. Turning that into `failEpisode` would be another refused write.

## The related fix: retry runs do not need the feed

The start handler in the plan fetches the RSS feed for every kind of run and selects from its entries. For an owner retry that is wasted work and a hazard: the selection is already fixed to one video, and if that video has aged out of the roughly fifteen entries the feed shows, a selection built from feed entries would not contain it. So when `startRun` is given a video id, it skips the fetch, passes `createRun` a selection of exactly that video, and leaves `last_checked_at` alone since nothing was checked.
````

````text
Three layers are involved, and each has one job.

**Layer 1: the adapter makes exactly one call.** `lib/transcripts/downsub.ts` sends one `GET /download?url=…` and maps the answer. A 429 becomes `throw new TranscriptError("PROVIDER_RATE_LIMIT")`. The adapter never retries, never sleeps, never looks at the clock. That keeps it a pure translation of DownSub's protocol and puts all timing decisions in one place, the step.

**Layer 2: the transcript step retries.** In the instance, the call sits inside `step.do("transcript", policy, fn)`. Workflows tracks the step's attempts durably, so the schedule survives even if the isolate running the instance dies between tries. The spec's policy is three retries with exponential backoff from ten seconds, and a two-minute timeout per attempt because DownSub's error paths can take up to a minute:

| Attempt | When | What a 429 costs |
|---|---|---|
| 1 | t = 0 | nothing, errors are not billed |
| 2 | t ≈ 10 s | nothing |
| 3 | t ≈ 30 s | nothing |
| 4 | t ≈ 70 s | nothing |

Whether a failure retries at all is decided inside `fn`:

```ts
() => source.fetch(videoId).catch((error) => {
  if (isNonRetryable(transcriptFailure(error))) throw new NonRetryableError(error.message);
  throw error;   // PROVIDER_RATE_LIMIT, PROVIDER_HTTP, PROVIDER_PARSE: let the step retry
})
```

`UNPLAYABLE`, `PROVIDER_AUTH`, `PROVIDER_LIMIT`, and `TRANSCRIPT_TOO_LARGE` are wrapped in `NonRetryableError`, so the step fails at once: retrying a wrong key or an empty credit balance gains nothing. A 429 is deliberately left retryable, because it means "not right now", which is exactly what a wait fixes. Before the step even runs, the stagger has already spread the tick's instances three seconds apart, so the retry schedule is the second line of defence, not the first. Together they give DownSub roughly seventy seconds of breathing room per episode at zero credit cost.

**Layer 3: what happens when the step gives up.** After the fourth 429, `step.do` throws. The instance's stage-one catch reads the reason from the message prefix and classifies it as account-level, then calls `markTranscript(runId, videoId, accountLevel(PROVIDER_RATE_LIMIT))`. The Registry leaves the episode `pending` with no wait reason and, crucially, does not increment `attempt_count`. Its run-episode becomes `not_attempted PROVIDER_RATE_LIMIT`, and the instance ends. When the run's last row resolves, the precedence rule closes the run `failed PROVIDER_RATE_LIMIT` unless a key, credit, or lost-instance code outranks it. The channel then counts in `attention.failedRuns` and sits under "Last run failed" with Start. The next cron tick, at most six hours later, reselects the episode because it is still `pending` with attempts below three, and the whole sequence runs again.

**Why the attempt count is untouched.** A `PROVIDER_HTTP` after the same four tries would count one attempt, and three such runs would make the episode `failed` for the owner.
````
