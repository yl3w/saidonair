### Replied · 2026-09-13 08:51

```text
Today they are not guaranteed to be in sync, and nothing detects when they are not. Here is what exists, where it breaks, and what I would do.

**What exists**

Every follow write goes User DO first, then Registry, from four routes: follow, unfollow, add channel, and request again. The PRD's promise, in §4.3, is that both writes are idempotent and that a pair left inconsistent by a failure is corrected by the next follow or unfollow of that same pair. There is no transaction across Durable Objects, so that promise is the whole mechanism.

**Where it breaks**

- Follow lands in the User DO, the Registry call fails. The user sees "following" and gets the channel in their digest and unread counts, because eligibility reads the User DO. The Registry counts nobody, so a channel nobody else follows stays system-paused and is never discovered. The user has followed a channel that will silently never produce anything, until they unfollow and follow again.
- Unfollow lands in the User DO, the Registry call fails. The owner sees a phantom follower and the channel keeps being discovered for nobody. This also costs transcript credits.
- Nothing repairs either case except the same user acting on the same channel again. The web shows `following` from one store and `followerCount` from the other, so it can display a follow of a channel with zero followers, and no test covers any drift case.

**Options**

| Option | What it gives | Cost |
|---|---|---|
| Keep the split, flip to Registry-first | Trades the silent paused-channel case for a visible one: the user does not see the follow yet the count includes them | Still two truths, still no detection |
| Keep the split, reconcile in the cron | Detects and repairs drift every six hours, User DO winning | Enumerates every user's DO each tick; drift lives up to six hours |
| Keep the split, outbox with a DO alarm | The classic reliable dual write: the User DO records the intent and retries the Registry until it succeeds | The most machinery of the four |
| One owner: the Registry holds follows, the User DO does not | Nothing to sync. Eligibility becomes one SQL join in the Registry instead of a cross-DO round trip | A PRD and schema change; the Registry is the only source for a user's list |

**My recommendation is the last one.** The duplication buys nothing today. The Registry row and the User DO row carry the same two timestamps, follows are already visible to the Registry by design so there is no privacy gained by the copy, and every Home load already goes through the Registry for channels and the catalog. The User DO would keep what is truly private: read receipts, chats, and preferences. This is a "maintainable over clever" call, and now is the cheapest moment, with governance open and nothing deployed.

What it touches: PRD §2, §4.3, §5.2, and §8, the User DO's `0001` losing `channel_follows`, the User DO's follow store and RPC methods, the eligibility helper, the follow and channel routes, AGENTS.md's two sentences on the follower record, and the tests. A day's step, not a milestone.

If you would rather keep follows in the User DO for a reason I am not seeing, the outbox is the honest way to make the promise in §4.3 true; the reconciling cron is the cheap way. Say which and I will write the spec change.
```
