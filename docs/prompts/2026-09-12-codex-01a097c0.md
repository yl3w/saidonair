## Findings

1. **High — Non-owners can control owner-owned channel settings.**  
   [`CreateChannelBody`](/Users/bhaskar/workspace/media-digest-assistant/docs/specs/api-reference.md:207) permits `title` and `initialImportCount` for the anyone-accessible `POST /channels`. The PRD says the RSS title may be overridden by the owner and the import count is owner-configurable ([PRD](/Users/bhaskar/workspace/media-digest-assistant/docs/PRD.md:136)). The current handler passes both fields into `createChannel` regardless of role ([channels.ts](/Users/bhaskar/workspace/media-digest-assistant/apps/api/src/routes/channels.ts:145)), and the plan does not correct this. A requester can therefore choose shared catalog metadata and the eventual import size. The spec needs to decide whether non-owner values are rejected or ignored and plan that behavior explicitly.

2. **High — Retry omits a valid synchronous `failed WORKFLOW_LOST` response.**  
   The spec says `EpisodeRetryResponse.attempt` is “running, or blocked” ([api-reference.md](/Users/bhaskar/workspace/media-digest-assistant/docs/specs/api-reference.md:260)). The PRD requires a Workflow creation failure to finish that newly created attempt immediately as `failed WORKFLOW_LOST` ([PRD](/Users/bhaskar/workspace/media-digest-assistant/docs/PRD.md:207)), while Retry returns the new attempt. The enum technically permits it, but the prose and planned tests do not. Document and test all three immediate outcomes: `running`, `blocked`, and `failed WORKFLOW_LOST`.

3. **High — The coupled, approved M3 plan remains contradictory.**  
   The API spec acknowledges that M3 Step 3 is superseded but leaves a `TODO(owner)` to amend it ([api-reference.md](/Users/bhaskar/workspace/media-digest-assistant/docs/specs/api-reference.md:417)). Those conflict with the PRD and the new API contract. Because API plan Step 3 is explicitly coupled to M3 Step 4, the M3 plan must be updated as part of this approval rather than left as an executable conflicting plan.
