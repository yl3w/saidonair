### Replied · 2026-09-14 09:15

```text
## Can you use shadcn?

Technically yes, but not cleanly on this stack, and the reason matters. shadcn assumes React. Your web app is Preact, and shadcn's interactive primitives reach into React internals, which is exactly where Preact's compatibility layer is thinnest. Aliasing is already available to you through the Preact Vite preset, so the experiment is cheap to try and expensive to trust.

Three things changed the picture since the library's early days. As of July 2026 shadcn defaults to Base UI rather than Radix, Radix is still supported behind an init flag, and an unofficial Preact port exists. None of those is a compatibility guarantee for Preact, and your web app has no tests at all, so nothing would catch a primitive that renders but misbehaves.

Size is the argument I expected to make against it, and honestly it does not hold. Your entire application today is smaller than most single components:

| Asset | Gzipped |
|---|---|
| All JavaScript | 17.6 KB |
| All CSS | 1.0 KB |

A shadcn build would plausibly land between 80 and 140 KB gzipped once Base UI, a styling tool, the class utilities, and icons arrive. That is a five to sevenfold increase, and still fast enough for your five-second Home target. So decide this on maintenance and identity, not on kilobytes.

## Four approaches

**Tokens and hand-built components, current stack.** Formalize what you have. The existing stylesheet is already 282 lines of semantic classes, so this is mostly promotion rather than rewriting. Use the platform for the two hard primitives, the native dialog element for confirmations and details for the collapsed review history, which buys real accessibility without a dependency. Pros: no compatibility risk, no new approved dependencies, a look that is yours, and it honors the rule you reaffirmed this morning. Cons: you build your own focus management, and there is no component documentation for free.

**shadcn through Preact aliasing.** Pros: fast start, conventional result. Cons: you are betting on an untested combination with no test suite underneath it, and every future library update reopens the bet. This is the option I would avoid, because it carries the cost of a dependency and the risk of a fork.

**The unofficial Preact port.** Pros: removes the aliasing layer. Cons: a single-maintainer project between you and your interface for a tool you have described as long-lived. Your own hard rule about dependencies exists for this.

**Move the web to React and use shadcn natively.** Pros: the only honest way to get shadcn properly, plus a large ecosystem. Cons: it changes the stack decision, adds real weight, and gives your product the shadcn look, which is the most recognizable interface style of the last two years. For a personal reading tool that is an identity cost, not a neutral default.

My recommendation is the first, and the reason is in your own screens rather than in any library.

## What reviewing the specification turned up

**You have two products, and a component library serves only one.** The digest is a reading surface. The Owner screens are an operations console with a ten-column table, status counts, and row actions. shadcn is tuned for the console and adds almost nothing to the reading experience. A single library applied to both would flatten a distinction the design should be sharpening.

**The real design problem is a state vocabulary, not components.** Between three channel statuses, a pause flag, fifteen attempt outcome codes, wait reasons, skip reasons, window intents, and run results, a reader or owner has roughly twenty-five states to tell apart at a glance. No component library solves that. It needs severity, permanence, and who-must-act encoded consistently in form as well as words. That is where the design investment pays, and your copy module is already the right foundation for it.

**Thumbnails are your biggest cheap win, and they conflict with a stated constraint.** Channel avatars and video thumbnails would turn the digest from a flat text list into something scannable, which is the main thing your rule change unlocks. But the specification says the only external services called are the YouTube feed, Cloudflare, and the transcript provider. Thumbnails would make every reader's browser fetch images from Google's image host. Given how explicit the privacy section is, that needs a deliberate decision rather than arriving as a side effect of a design.

**Home is about to be doing four jobs on one scroll.** Digest, followed channels, catalog and an add form, with conversations still to come. Anchored sections were a reasonable choice for two jobs. The specification also forbids client-side tab state, so that rule is worth revisiting explicitly in the design phase rather than designing around it.

**Nothing says whether the Owner screens must work on a phone.** A ten-column catalog table cannot survive 400 pixels intact. Reader screens and owner screens may deserve different width commitments, and that is a decision, not a detail.

I can turn this into the design phase specification, where these become decisions with rationale in your usual format. Say the word and I will draft the spec and plan.

Sources: [shadcn Base UI changelog](https://ui.shadcn.com/docs/changelog/2026-07-base-ui-default), [Radix Preact compatibility discussion](https://github.com/radix-ui/primitives/discussions/807), [Preact component library discussion](https://github.com/preactjs/preact/discussions/4559), [shadcn-preact port](https://github.com/LiasCode/shadcn-preact)
```

```text
## Verdict

DaisyUI is a much better fit than shadcn, and it solves the exact problem that ruled shadcn out. It is a Tailwind plugin that ships pure CSS class names with no JavaScript bundle, and it is explicitly framework agnostic. The Preact compatibility question disappears entirely, because there is no React to be compatible with. Version 5.7.37 was published three days ago, so it is actively maintained.

The size picture is the strongest argument. DaisyUI adds no runtime JavaScript at all, so your bundle grows only in CSS:

| | JavaScript | CSS |
|---|---|---|
| Today, measured | 17.6 KB | 1.0 KB |
| With DaisyUI, estimated | 17.6 KB | 12 to 20 KB |
| With shadcn, estimated | 80 to 130 KB | 10 to 20 KB |

The entire DaisyUI stylesheet with all 68 components and every theme is 34 KB compressed, and the Tailwind plugin ships only the classes you actually use. So you get a component library for roughly the cost of a photograph, and your JavaScript never moves.

Installation is three build-time packages and two lines of CSS. Nothing is added to what the browser executes.

## How it maps onto your screens

This is what moved me from neutral to positive. The component set lines up with your specification unusually well, including the parts I said no library would help with:

- **Badge, status, and indicator** for the state vocabulary. This is your largest design problem and DaisyUI gives it real primitives.
- **Stat** for the catalog health strip, which is exactly channels by status, credits, and last ingestion.
- **Table** for the ten-column owner catalog.
- **Collapse** for the reviewed history your specification already says is collapsed.
- **Alert** for decline notes, owner notes, and row action failures.
- **Skeleton** for the per-section loading states, which today have no visual treatment.
- **Avatar** for channel avatars, newly permitted by this morning's rule change.
- **Modal** for the confirm-once actions, and the recommended method is the native dialog element with escape-key closing and focus containment. That is precisely the accessible primitive I suggested hand-building, so you get it for free.
- **Chat bubbles** for the conversations milestone, with distinct sides and space for source links.
- **Tooltip** for explaining the disabled Retry button.

Identity is also manageable, which was my main objection to shadcn. You can define one custom theme in oklch colors and exclude all 35 built-ins, so nothing ships but your own palette, with a flag that makes a theme the dark-mode default. The product would not look like default DaisyUI unless you let it.

## What you are actually signing up for

Four honest costs, in the order I would weigh them.

**Tailwind comes with it, and that is the real decision.** You are not adopting a component library, you are adopting a styling system. This reverses two stated rules, the one plain CSS file and the no CSS framework clause, and it retires your 282-line stylesheet in favor of classes in markup. DaisyUI softens this more than raw Tailwind would, because its component classes are semantic rather than atomic, but layout still arrives as utilities in your components. For a codebase whose stated value is that maintainable beats clever, that readability cost is worth naming out loud rather than discovering in review.

**Accessibility becomes your responsibility per component.** Because it is only CSS, behavior is yours. Dropdowns lean on focus, the accordion uses radio inputs, and two of the four documented modal methods drop escape-key support. You have to pick the accessible variant every time and verify it by hand, and the web app still has no tests to catch a regression.

**One component collides with an existing rule.** DaisyUI's tabs are radio-input based, which is client-side tab state, and your specification requires anchors instead. Either avoid that component or change the rule deliberately.

**It gives you parts, not a system.** DaisyUI offers roughly five semantic colors and you have about twenty-five states to distinguish. Deciding which outcome is a warning, which is an error, which is merely informational, and which demands that the owner act is still design work that no library does for you. The library shortens the build, not the thinking.

My recommendation is to adopt it under four conditions: ship one custom theme with the built-ins excluded, permit only the native dialog modal method, keep your copy module as the single home for every phrase so the library supplies form and your code supplies words, and settle the tabs rule explicitly. The thumbnail privacy question I raised is unaffected by this choice and still needs a decision.

Say the word and I will record this as a dated decision, amend the dependency rule and the stack table to match, and draft the design phase specification around it.

Sources: [daisyUI docs](https://daisyui.com/docs/intro/), [components](https://daisyui.com/components/), [Vite install](https://daisyui.com/docs/install/vite/), [themes](https://daisyui.com/docs/themes/), [modal accessibility](https://daisyui.com/components/modal/), [npm package](https://www.npmjs.com/package/daisyui)
```
