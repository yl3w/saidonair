## Step 1 — two feeds in `rss.ts`

### 1.1 The two URL builders

`feedUrl` (`apps/api/src/lib/youtube/rss.ts:31`) is called from exactly one place: `fetchChannelFeed` at `:119`, which has already validated the id. The rename to `channelFeedUrl` is mechanical. The new one:

```ts
export function longFormFeedUrl(channelId: string): string {
  const id = requireChannelId(channelId);
  return `https://www.youtube.com/feeds/videos.xml?playlist_id=UULF${id.slice(2)}`;
}
```

Why validate *inside* this one when `channelFeedUrl` doesn't? Because `slice(2)` on an unvalidated string silently produces a plausible-looking wrong URL, where `channel_id=@handle` produces an obviously wrong one. Validating here means a malformed id throws before any fetch (spec §4.1). The double-validate when `fetchLongFormFeed` calls it is free.

### 1.2 One private fetcher, two public names

Today `fetchChannelFeed` (`:112`) holds five policies: validate the id, 404 → `null`, non-ok → `UPSTREAM_UNAVAILABLE`, parse failure → `UPSTREAM_UNAVAILABLE`, channel-id mismatch → `UPSTREAM_UNAVAILABLE`. None of those are *per-feed* policies; they're "what a feed read means" policies. So:

```ts
export async function fetchChannelFeed(channelId, fetchImpl = …) {
  const id = requireChannelId(channelId);
  return fetchFeed(channelFeedUrl(id), id, fetchImpl);
}

export async function fetchLongFormFeed(channelId, fetchImpl = …) {
  const id = requireChannelId(channelId);
  return fetchFeed(longFormFeedUrl(id), id, fetchImpl);
}

async function fetchFeed(url: string, expectedChannelId: string, fetchImpl: FetchLike) {
  /* the existing body of fetchChannelFeed from the try/fetch down to the return */
}
```

The point of `expectedChannelId` as a parameter rather than re-deriving it: the identity guard at `:146` must compare against the `UC…` id in both cases, even though the long-form URL carries `UULF…`. Pass it in and the guard can't get confused about which id shape it's holding.

### 1.3 The title rule — the one subtle bit

`parseFeed` (`:159`) currently does `textOf(head, "title")` and throws if absent. For the playlist feed that returns the literal string `"Videos"`, which would end up as the channel title on the owner's row. The fix is `<author><name>` first (spec §4.2: it's the channel name in *both* shapes).

Don't write `textOf(head, "name")`. Extract the `<author>` block first, then read `<name>` inside it:

```ts
function titleOf(head: string): string | null {
  const author = /<author>([\s\S]*?)<\/author>/.exec(head)?.[1];
  const name = author ? textOf(author, "name") : null;
  if (name) return name;
  return textOf(head, "title");
}
```

Two reasons. First, `textOf` takes the *first* match in the string you hand it, so scoping to the author block is what makes "the channel's name" rather than "whatever `<name>` appears first" true by construction. Second, `textOf` trims, so an empty `<name></name>` returns `""` — falsy, so the `if (name)` correctly falls through to `<title>` instead of setting the title to empty string. Then `parseFeed` throws "feed has no title" only when `titleOf` returns null.

`channelIdOf` (`:210`) needs **no code change** — that's worth understanding rather than taking on faith. It tries the alternate link, which the playlist head doesn't have, then falls back to `<yt:channelId>` and prepends `UC` only when missing (`bare.startsWith("UC") ? bare : \`UC${bare}\``). The channel feed strips the prefix, the playlist feed keeps it, and that ternary already covers both. Only the comment at `:1–8` is wrong — it says "the feed-level `<yt:channelId>` omits the `UC` prefix" as if universal. Correct it to name which feed does which.
