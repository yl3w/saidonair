````text
## Does `wrangler delete` take the Durable Objects with it?

I read the implementation rather than recalling it. In wrangler 4.129.0 the `delete` command confirms `Are you sure you want to delete <name>? This action cannot be undone.` and then calls `DELETE /accounts/<id>/workers/services/<name>`. **There is no Durable Object warning of any kind.** The only extra step is `deleteSiteNamespaceIfExisting`, which is about the legacy Workers Sites KV namespace, not DOs.

What Cloudflare documents is the *class*-level delete, never the Worker-level one:

- `deleted_classes` — "Running a Delete migration will delete all Durable Objects associated with the deleted class, including all of their stored data."
- the newer `exports` `deleted` tombstone — "Deleting a class destroys its data… There is no Trash for Durable Object namespaces deleted through `exports`."

Whether deleting the *whole Worker* cascades to its namespaces is **not stated on any page I checked** — migrations, legacy migrations, data location, or the Delete Worker API reference. Namespaces belong to the Worker service, so in practice they almost certainly go with it. But "almost certainly" is not a basis for a data-loss procedure, and a CLI that says nothing either way makes it worse. The plan settles it by experiment instead: once staging first deploys, write one row, delete, redeploy, read it back. Ten minutes, and the one unknown becomes a fact.

## Starting staging with a clean database

**The recommended route is a `deleted_classes` + re-add migration pair** — documented, certain, and surgical, touching DO data only while leaving secrets, routes and the Vectorize index alone:

```jsonc
{ "tag": "v3", "deleted_classes": ["RegistryDO", "UserDO"] },
{ "tag": "v4", "new_sqlite_classes": ["RegistryDO", "UserDO"] }
```

**There's a bad footgun here.** `migrations` is one of the three keys wrangler *inherits into every environment*. A wipe pair committed to `wrangler.jsonc` sits there and detonates on the next `deploy:production` too. So the pair is never committed — add it, deploy staging, revert. The plan makes that enforceable rather than remembered: `test/wrangler-config.test.ts` gains a case that fails if any committed migration tag carries `deleted_classes`, so `pnpm check` refuses to let one reach `main`.

The two alternatives lose. `wrangler delete` + redeploy is tempting since staging is disposable, but the cascade is unverified, it destroys both staging secrets every time, and it's the one command that would be catastrophic aimed one `--env` to the left. An app-level reset route is blocked outright — the API enforces no authorization at all, so `POST /admin/reset` on a deployed Worker would be an unauthenticated public wipe endpoint.

The consequence for the skill: this route is a config edit plus a deploy, not a command, so `clean-cloudflare-assets` can't perform it. Its "what this cannot clean" section names the procedure instead of leaving the impression that a staging clean emptied the environment.

Sources: [Durable Object class exports](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/), [legacy class migrations](https://developers.cloudflare.com/durable-objects/reference/durable-object-class-migrations-legacy/)
````

```text
Yes to both — but testing it turned up something you'd want to know about.

**Install is already "all".** `pnpm skills:install` passes `--skill '*' -y` to both sources, so it installs everything from `obra/superpowers` and `./skills` every time.

**Remove now takes `--all`:** `pnpm skills:remove --all` clears every installed skill from both agent directories and the lock.

**The thing worth knowing: the skills CLI deletes your source directory.** I tested `--all` end to end instead of trusting the help text, and it wiped `skills/` — the committed source, not just the agent copies. Then I checked whether that was specific to `--all`, and it isn't: removing a *single* named local skill does it too. Everything was committed, so `git restore skills/` recovered it immediately, and the source now matches HEAD exactly.

That made the advice I committed an hour ago in `8ee4a0e` — "run `pnpm skills:remove <old-name> -y` on a rename" — unsafe. It happened to work because the old name no longer exists under `skills/` by then, but that's a fragile thing to depend on.

`2c1de35` fixes it. `skills:remove` snapshots `skills/` before calling the CLI and restores anything it eats, printing a note when it does. I used a snapshot rather than `git restore` so uncommitted edits to a skill survive too.

I did consider the simpler fix of always passing `--agent`, which avoids the deletion. I rejected it: removal is then per-agent-registration, and `.agents/skills/` is shared by Codex, Copilot and OpenClaw, so the directory survives while any one of them still claims it — `--agent codex` reported "removed 1 skill" and left the files sitting there. The unscoped form is the one that actually removes things, so it was worth keeping and neutralizing.

Round-tripped after the fix: `--all` clears 15 from both directories and the lock, `skills/` stays intact, `pnpm skills:install` restores all 15. `pnpm check` green, and your working tree is back to full state.
```
