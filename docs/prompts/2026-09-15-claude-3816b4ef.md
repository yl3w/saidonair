## What's actually happening

Three separate things are tangled together here. Worth pulling them apart, because they have different causes.

**1. The back arrow is hardcoded.** `Reading.tsx:89-94` is literally `<a href="/queue">` with the label "Back to the queue". It doesn't matter where you came from — it always says the queue and always goes there. That's not a bug in some routing layer; it's a link that was written when the queue was the only way in. Since then History and a source page both got rows that open a summary, and neither is reachable from the arrow.

**2. Your position in the list is lost.** The browser's own back button *does* return you to History (preact-iso pushes a real history entry when you click a row title). But the list re-fetches its rows from the API on the way back, so for a moment the page is empty and short — and the browser, trying to restore your scroll position while the page is still one screen tall, gives up and leaves you at the top. By the time the rows land, the moment has passed. So even the browser back, which routes correctly, drops you at the top of a 200-row list.

**3. Done is offered on episodes that are already done.** The condition at `Reading.tsx:148-150` is `episode.read !== undefined` — which is true for *any* eligible reader, whether or not they've read it. It should be `episode.read === false`. And there's a second surprise you didn't name, which I think is the same bug wearing a different hat: pressing Done on a genuinely **unread** episode that you opened **from History** also flings you into the next unread item in the queue. You were browsing a library; the product decided you were working a conveyor belt.

## On your recommendation

I accept the first half as written — preserve the originating route and position — with one change to *how* position is preserved. On the second half I'd take "omit it" over "Next unread", and go a little further.

**Why not "Next unread" as a button.** It reads like a caption for what the button does, but it's really a new feature: a jump into the queue from somewhere that isn't the queue. The design guide's third principle keeps those two jobs apart on purpose — the queue answers "what still needs me", History answers "what arrived and when" — and a button that teleports you from the library into the conveyor is exactly the mixing that principle exists to prevent. If someone wants the next unread thing, the queue is one nav click away and it's already the product's front door.

**Why not Undo there either**, since it's the obvious other candidate: `docs/design.md` §4 already rules on this — "Undo lives where the consequence is visible. A read receipt can be undone in History, where the row is, and nowhere else."

So on a read episode the header simply has no action, and the meta line gains the word **Read**, matching what the row said in the list it came from. The state is stated rather than implied by an absent button — which is the "state is a fact, not a feeling" rule.

## On preserving position: pixels vs. the row

This is the one place I'd diverge from a literal reading of your recommendation. Remembering a **scroll offset in pixels** is fragile here for three reasons specific to this product: the density switch changes every row's height, so returning at 4,000 px lands somewhere else entirely; History and the queue page in with "Show more", so an offset from three loaded pages is unreachable when only one page has re-loaded; and if you pressed Done, the row you were looking at is *gone* from the queue, so the offset now points at a different episode.

Anchoring on **the row's identity** instead is both simpler and better behaved: remember which episode you opened, and on return scroll that row back into view once the rows are actually in the DOM. If the row is no longer there — you marked it done and it left the queue — fall back to its day heading, which is still there. If neither exists, the top.

Known limit, which I'd rather state than paper over: if you opened a row from the third "Show more" page, coming back reloads only the first page and you land at the top. Fixing that properly means remembering how many pages were open and refetching them, which I'd leave until it actually annoys you.

|---|---|---|
| Arrow | Opened from the queue, or cold deep link | "Back to the queue" → `/queue` |

| | Opened from a source | "Back to *Computerphile*" → that source page |
| Action | Unread, opened from the queue (or no origin) | **Done** → receipt, then the next unread, as today |
| | Unread, opened from History or a source | **Done** → receipt, then back to that list, your row still there and marked read |
| | Already read | *no button*; the meta line reads "Read" |
