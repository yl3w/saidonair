```text
Both gaps are the same shape: the spec described a route as if it already existed, and it didn't. They only surfaced when I went to call them.

## `/preferences` (Step 4)

PRD §7's route table has listed `GET /preferences` and `PUT /preferences` since the 2026-09-12 restart. The shared schemas were written (`PreferencesSchema`, `PreferencesResponseSchema`, `UpdatePreferencesBodySchema`), and the User DO has `getPreferences`/`setPreferences` with a migration and tests. Nothing registered them, so they weren't in `openapi.test.ts`'s operation list either — and that test only fails when a *registered* route is missing from the document, never when a documented-in-the-PRD route was never registered.

So when Step 4's Account screen went to save `system_rules` — which spec §4.7 requires — there was nothing to call. I wrote the two handlers and their tests.

## `GET /episodes/:episodeId` (Step 5)

This one is more interesting, because the spec contradicts itself in a single sentence. §4.3:

> `GET /channels/:channelId/episodes/:episodeId` returns one episode with its summary, related items and read state, **so `/read/:episodeId` is a deep link that works on a cold load**.

The browser URL carries one id. The API route needs two. A cold load — pasting the link, reloading, arriving from outside — is by definition the case where the client knows only what's in the URL, so it cannot supply the channel. The sentence reads fine in prose and doesn't survive contact with the address bar.

It works when you *click* a queue row, because the client already holds the whole `Episode` object including `channelId`. That's exactly the case the spec says must also work without.

What I considered:

- **Pass the channel through router state or a query param.** Works on click, fails on paste and reload. That's the named requirement, so no.
- **`/read/:channelId/:episodeId`.** Contradicts the approved route table in §4.2, and puts two opaque ids in the product's most shareable URL.
- **Find the episode in an already-loaded list.** Unreliable — a read episode isn't in the queue at all, and anything past the first page isn't loaded.
- **Add `GET /episodes/:episodeId`.** What I did.

The justification is that `episodes.episode_id` is `TEXT PRIMARY KEY` — unique across the whole catalog, not per channel. So the channel segment in `/channels/:id/episodes/:episodeId` was never part of the identifier; it was a scope check. An episode can name itself, and the reading view addresses a summary rather than a channel's episode.

I kept the channel-scoped route rather than replacing it: it 404s when the episode belongs to a different channel, which is what a caller that already knows the channel wants, and Curate walks episodes that way. The two receipt routes stayed channel-scoped too, and that's fine — by the time Done is pressed the client has the loaded episode and its `channelId`.

## Why I flagged it rather than just doing it quietly

Two things for you to weigh:

1. **I resolved a doc-vs-code disagreement by changing the code.** You might prefer the reading view live at `/read/:channelId/:episodeId` and keep the API surface as specified, or go further and make every episode-scoped route top-level (`POST /episodes/:episodeId/read`), which is arguably the more consistent shape now that the id names itself. Both are cheap to change today and expensive once the screens are built on them.

2. **The pattern suggests where to look next.** Both gaps come from the same place: specs are reviewed against the PRD, and in both cases the PRD is where the mistake already was. Steps 6–8 lean on `/digest` with `compact`, the channel list and Curate's existing routes — all of which I've now touched or exercised — so I don't expect a third. But it's worth knowing the review loop can't catch this class on its own.

One piece of bookkeeping that follows from it: plan Step 9.2 says PRD §7's route table "takes the Step 1 and 2 changes" — written before Steps 4 and 5 added routes. I can amend that line now so the two new routes aren't lost at the end, or just carry it in memory and handle it when Step 9 comes. Say which.
```
