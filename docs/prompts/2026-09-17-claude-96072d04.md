````text
## What's happening

Two things, and the second one hides the first.

**1. Tailwind v4 stopped setting it.** `apps/web` is on `<email>` (`apps/web/package.json:18`). Tailwind v3's Preflight contained `button, [role="button"] { cursor: pointer }`. v4 deliberately dropped it to match the browser's own stylesheet, where a `<button>` is `cursor: default` — the arrow. I grepped the installed Preflight to be sure: the only `cursor` in `node_modules/.pnpm/<email>/node_modules/tailwindcss/preflight.css` is a comment at line 384 about Safari spin buttons. Nothing sets the hand.

Nothing in the app sets it either. `apps/web/src/styles.css` has no `cursor` declaration at all, and the only one in the whole web source is `disabled:cursor-not-allowed` at `apps/web/src/components/ChannelStatusActions.tsx:182`.

**2. daisyUI masks it for about half the buttons.** daisyUI's `.btn` sets `cursor: pointer` in its own component CSS. So of the 43 `<button>` elements in `apps/web/src`, the 21 carrying `class="btn …"` (Queue, Reading, Sheet, ConfirmDialog, AddChannel, Account…) behave correctly, and the 22 hand-rolled ones do not:

- every icon button — `size-11` back arrows and toggles in `Chat.tsx:158`, `Source.tsx:261`, `Calendar.tsx:104`/`111`, `CurateChannel.tsx:348`, `ScopeChip.tsx:28`, `SummaryRow.tsx:121`
- `FollowButton.tsx:40`, `Retry.tsx:16`, the `ChannelStatusActions` pair at `:173`/`:222`
- the filter and sort affordances — `ChannelFilter.tsx:78`/`175`/`199`, `CatalogHealth.tsx:56`, `CatalogTable.tsx:100`, `Source.tsx:169`, `History.tsx:116`
- calendar day cells, `Calendar.tsx:194`

Links are unaffected: `<a href>` still gets the hand from the UA stylesheet. That mix — links right, `.btn` right, icon buttons wrong — is exactly the inconsistency you're feeling.

(Terminology, so we're speaking the same language: the hand *is* `cursor: pointer` in CSS; the arrow you're getting is `cursor: default`.)

## The fix

One base-layer rule in `apps/web/src/styles.css`, next to the focus-visible rule at line 260, fixes all 22 at once and anything added later:

```css
  /* Tailwind v4's Preflight leaves a <button> at the UA default arrow; daisyUI's .btn sets the
   * hand itself, so half the controls said "clickable" and half didn't. Say it once, here. */
  button:not(:disabled),
  [role="button"]:not(:disabled),
  label:has(> input[type="checkbox"], > input[type="radio"]),
  summary {
    cursor: pointer;
  }
```

The `label` clause covers the checkbox row at `Settings.tsx:172`, which is clickable for the same reason and equally silent about it.

Two things I'd want your call on before touching it, since per AGENTS.md this is a `docs/design.md` §4 change and that section currently says nothing about cursors:

1. **Disabled controls.** My rule above leaves them at the arrow, which pairs with the existing "an unavailable control must look unavailable". That makes the lone `disabled:cursor-not-allowed` in `ChannelStatusActions.tsx:182` the odd one out — drop it, or standardise on `not-allowed` everywhere instead?
2. Want me to apply it and add the interaction rule to `docs/design.md` §4?
````

````text
You're right to push back — and the evidence says the cursor isn't the actual defect.

## The reframe

The cursor is the **weakest and last** affordance: it doesn't exist on touch, it only appears after someone has already guessed and moved the mouse there, and it says nothing to keyboard or screen-reader users. It should *confirm* a guess the design already invited. If it's how we announce clickability, we've already lost.

The reason you noticed it here is that it was carrying the entire load. `grep -c "hover:" apps/web/src` → **0**. Not one hover state in 43 buttons.

## And the daisyUI buttons are hover-dead too

This is the part worth knowing. daisyUI's `.btn` hover works by *reassigning a variable* — I pulled it from the build output:

```css
.btn { --btn-bg: …; background-color: var(--btn-bg) }
.btn:hover { --btn-bg: color-mix(in oklab, …, #000 7%) }   /* swaps the variable */
.bg-panel { background-color: var(--panel) }                /* sets the property */
```

All 21 `.btn` call sites carry `border-edge bg-panel text-ui text-primary` (`Queue.tsx:177`, `Sheet.tsx:67`, `ConfirmDialog.tsx:54`, …). `bg-panel` pins `background-color` directly, so daisyUI's `--btn-bg` swap resolves into nothing — and `.bg-panel` sits in the unnamed utilities layer while `.btn` sits in `daisyui.l1.l2.l3`, so it wins on layer order regardless of specificity. `border-edge` and `text-primary` kill the border and text halves of the hover the same way.

So the real finding is: **we use daisyUI's shape and override away its behaviour**, then hand-roll 22 more controls with no behaviour at all (`Chat.tsx:158` is a bare 44px glyph — no container, no border, no hover, nothing).

That's what you felt. The missing cursor was the only symptom visible enough to name.

## Using the stack as intended

**1. Give the 22 hand-rolled controls a daisyUI component role.** `btn-ghost` is the one this product wants — it paints no background at rest and its hover sets `background-color` *directly* (a 10% `base-content` wash, i.e. a quiet ink tint on panel), so it survives without any call-site override:

| Today | daisyUI |
|---|---|
| `flex size-11 items-center justify-center text-ink-2` (`Chat.tsx:158`, `Calendar.tsx:104/111`, `Source.tsx:261`, `ScopeChip.tsx:28`) | `btn btn-ghost btn-square` |
| `min-h-11 px-2 text-ui text-primary` (`SummaryRow.tsx:133`, `Retry.tsx:16`) | `btn btn-link btn-sm` |
| filter/sort toggles (`ChannelFilter.tsx:78`, `CatalogHealth.tsx:56`, `CatalogTable.tsx:100`) | `btn btn-ghost btn-sm` + `btn-active` for the pressed one |

Hover, pressed, disabled, cursor and sizing all arrive together, from classes, with no new CSS.

**2. Stop re-skinning `.btn` inline.** That repeated `border-edge bg-panel text-ui text-primary` *is* the design guide's default button — it belongs in the `@plugin "daisyui/theme"` block at `styles.css:190` (or one `@utility`), not at 21 call sites where it silently disables the component.

**3. `@utility` for what daisyUI has no name for** — a calendar day cell, say. Tailwind v4's `@utility` is the framework's *official* extension API, so this isn't hacking; it keeps the rule in `styles.css` where the guide already insists all CSS lives.

The blanket `button { cursor: pointer }` I sketched last turn treats the symptom: it would paint "clickable" onto controls that still give no feedback when you actually hover them. Worth keeping as a one-line safety net *after* 1–3, not instead.

## The guide rule underneath it

`docs/design.md` §4 says a control must *look unavailable* when disabled, but never says a control must look available. That gap is why this shipped. Something like: **"A control announces itself before it is touched, and acknowledges the touch."** Rest form, hover, pressed — focus is already covered globally at `styles.css:260`.

Want me to spec this as a design.md §4 change plus the reclassification of the 43 controls, before touching code?
````

````text
Because I gave those rows the wrong component. They were `btn btn-ghost btn-block justify-start`, and `.btn` carries two declarations a list row must not have:

```css
.btn { text-align: center; font-weight: 600 }
```

`justify-start` only moves the flex *children* — the check slot, avatar, title span, count. Inside the title span, which is `flex-1` and therefore grows, `text-align: center` still centres the text. So every name floats in the middle of whatever space it has, and three names of three lengths get three different left edges. That's exactly what the screenshot shows: "Otherworld" indented further than "First Things First", further than "The Knowledge Project Pod…". The bold is the other half — those titles were regular weight before.

## Fixed

A list of choices in a popover is `menu`, not `btn` — daisyUI has the component:

- the list is `<ul class="menu max-h-72 w-full flex-nowrap overflow-y-auto">`, and each row a plain `<button class="flex">`. `.menu li > *` supplies `text-align: start`, padding, radius, hover and cursor, and says nothing about weight.
- `flex-nowrap` because `.menu` is `flex-flow: column wrap` — inside a scroll box it would have wrapped into a second column instead of scrolling.
- `flex` on the row because this row has four slots and daisyUI's menu grid assumes three (`minmax(auto,max-content) auto max-content`), which would have stretched the avatar's cell and stopped the title truncating.
- "Show every channel" became a second one-row `menu` so it matches.
- `Account.tsx:91` had the identical defect — same `btn-block` list — and got its `text-left` back.

Those were the only two full-width buttons in the app; nothing else has a growing child where centring shows.

The box you can see around the search field isn't an extra border — it's the popover's own edge on three sides and the list's `border-t` divider on the fourth. The field itself is `input input-ghost`, which is transparent.

`pnpm check` is green.

Worth saying plainly: my audit couldn't have caught this. It checked that no utility overrode a daisyUI declaration, and these rows passed — the classes were all daisyUI's. The mistake was choosing a button component for a list row, which only shows up when you open the screen. I've added that to `docs/design.md` §2.6 as its own rule, since it's the trap the next person will hit.
````
